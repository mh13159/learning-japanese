### Functional changes

1. **Hiragana ↔ Katakana split.** The UI now has 5 output cards (English / Japanese / Hiragana / Katakana / Romaji). Earlier "Kana" was hiragana-only; katakana was missing. Kuroshiro now runs three conversions in parallel per request (hiragana, katakana, romaji) and the legacy `kana` field is aliased to `hiragana` for any external consumers.

2. **NLLB-200 sentence translator (scripts/mt_server.py).** Self-hosted FastAPI service exposing the LibreTranslate `/translate` shape, backed by `facebook/nllb-200-distilled-600M`. Drop-in replacement: set `LIBRETRANSLATE_URL=http://localhost:5001`. Quality is night-and-day better than the Argos default — `where is the airport` was `空港の場所` (literal "airport's place") with Argos and is `空港はどこですか?` with NLLB. Tried three models before settling: Helsinki-NLP/opus-mt-en-jap (mangled output), staka/fugumt-en-ja (drops proper nouns), NLLB-200 (winner).

3. **CTranslate2 INT8 — 8x sentence speedup.** PyTorch FP32 was 7–10 s per sentence; CT2 INT8 is 0.9–2 s. Conversion is auto-bootstrapped on first server startup (`~/.cache/nllb-200-ct2-int8/`, ~600 MB). Quality unchanged or marginally better (Mount Fuji renders as 富士山 with proper kanji now, was フジ山 before).

4. **Stale-card UX fix.** When the user changed the input mid-debounce, the previous translation stayed visible until the new one arrived (the screenshot bug — "he is riding a bicycle" with `hello`/どうも showing). Cards now clear immediately on input change; loading skeletons render. Debounce bumped 400 ms → 700 ms now that the model is sub-second.

5. **Romaji overflow fix.** Long unbroken strings like `watashiwanipponoaishiteimasu` were overflowing the card. Added `overflow-wrap: anywhere` + `break-words` to the value div.

6. **Don't cache failed translations.** Previous code memoized empty results, so a transient MT-server timeout left a sticky "Japanese unavailable" entry. Now only successful results are cached. The note text also stopped saying "LibreTranslate" — it now mentions the MT server and suggests retry on transient failure.

7. **Install ergonomics.** `install.sh` (WSL / Linux / macOS) and `install.ps1` (Windows PowerShell), both idempotent. `requirements.txt` pins Python deps with `--extra-index-url https://download.pytorch.org/whl/cpu` so torch installs CPU-only.

8. **README rewrite.** Mermaid architecture diagram, Minimum + Recommended system requirements table, install-script quickstart, quality/latency comparison tables, licenses section. Vestigial multi-provider AI claims removed.

## Quality ceiling — discussed but not acted on

User compared our app's Japanese rendering of *"I vibe coded an app to get translation from English to Romaji to Japanese to Kana to Hiragana and the other way around as well."* against Google Translate's reverse translation. Two findings:

1. **NLLB-distilled-600M doesn't know modern slang.** "vibe coded" → "バイブで" (vibration). The slang ("vibe coded" = built with AI assistance) post-dates NLLB-200's training. Google's commercial model has it; no FOSS distilled model does.
2. **"ロマジ" katakana round-trips to "Romance" via Google.** Cosmetic — we should be producing "ローマ字" (kanji form) instead of phonetic katakana for that word.

Upgrade paths surfaced to the user:

| Option | Size after INT8 | Quality gain | Cost |
|---|---|---|---|
| NLLB-200-distilled-1.3B | ~2.5 GB | Noticeable on slang / long compounds | 2x latency + RAM |
| NLLB-200-3.3B (full) | ~6.5 GB | Closest to Google quality | 5–8x slower CPU, ~16 GB RAM, GPU recommended |
| M2M100-1.2B | ~2.5 GB | Sometimes better on Japanese phrasing | Older corpus |

All are drop-in via the `MODEL_NAME` constant in `scripts/mt_server.py` plus a re-run of `ct2-transformers-converter`. User has not picked one yet — they were observing the limitation, not requesting a fix.
